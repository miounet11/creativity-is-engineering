# 定律：慢是护城河

当操作者说「主要慢在输入」时，先分段计时，再决定动不动。

## 故事

一条长跑链路平均约 106 秒，成功率约 93%，吞吐约 3.6/min。操作者盯着表单页，看见姓名和密码一个字一个字蹦出来，认定瓶颈是打字。

分段之后：

| 阶段 | 大约墙钟 |
|------|----------|
| 启动浏览器 | 5s |
| 打开页面 | 7s |
| 邮箱阶段 | 5s |
| 等待并填写一次性代码 | 29s |
| 资料页（输入 + 人机验证并行） | 42s |
| 提交后取会话 | 18s |

资料页用的是「小心」档真人输入：约 26 个字符、字段切换、动作间停顿，肉眼 8–12 秒。人机验证与填表并行，墙钟 ≈ max(打字, 验证)，不是相加。把打字改成瞬间填完，资料页大约 42→33 秒，全链路 106→97 秒，吞吐大约 3.6→3.9/min。

**观感上的最大痛点，不是吞吐上的最大杠杆。** 而这段慢，正是行为层区别于脚本的部分。

## 定律

1. 没有分段计时，不准优化「慢」
2. 并行阶段看 max，不看 sum
3. 行为真实度是产品能力，不是性能债
4. 操作者可以说「别动这段」——这是产品判断，AI 必须遵守并写成 invariant

## 反例

「先把 typing_delay 调到 0，反正能过。」  
过一次 ≠ 过一个业务周期。护城河被优化掉之后，分类器会开始报另一类失败，而你已经失去对照。

## 落地

- 日志打累计时间戳，相减得各段
- 预设分档：`careful` / `default` / `realistic`，默认偏谨慎
- 若必须加速，只允许在**非护城河字段**上做 per-call override，并单独记一笔风险
