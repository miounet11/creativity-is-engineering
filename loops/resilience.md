# 闭环：长跑容错

从真实长跑排障抽出。不绑定某一家供应方、某一个站点、某一个浏览器。换平台时同一套步骤仍适用。

核心原则：**先看原文，再决定动作。不同失败不能合成同一种处理。任何一层卡住都要能换路，不能停机。**

---

## 1. 先取证，再归类

不要凭印象说「对方不认这种资源」。先存失败现场，再用原文做分类器。同一句「失败」至少要能拆出：

| 类型 | 典型信号 | 正确动作 |
|------|----------|----------|
| 资源被拒 | 域 / 号段已被拒绝 | 立刻退役 + 申诉 + 拉黑该资源，换下一个 |
| 频控 | N 分钟后再试 | 停发、冷却 N 分钟；去收件箱捞已有码；不重提 |
| 已发出 | 已向 xxx 发送一次性代码 | 留在当前页等，加长窗口，不关窗重提 |
| 校验错 | code invalid | 再拉一次最新码填一次；仍错再退役 |
| 已占用 | already exists | 退役 + 按「已使用」申诉 |
| 通道问题 | 代理墙、地区不可用、隧道失败 | 换通道，已买资源不动 |
| 基础设施 | 接口超时、进程起不来、内存不够 | 退避 / 降并发 / 延后副作用，不把业务资源判死 |

分类器写成纯函数并配单元测试，把真实句子贴进测试。

## 2. 一种问题只做一种事

| 动作 | 何时 |
|------|------|
| refund | 对方明确说不可用 / 已占用 / 校验错且刷新无效 |
| cooldown | 对方明确给了等待时间 |
| wait | 对方说已经寄出 |
| retry-channel | 网络 / 代理 / 启动失败 |
| shed | CPU / 内存过高 |
| defer | 主流程已成功、下游导入失败 → 本地落盘，稍后补推 |

禁止：用重提治疗频控；用整类停买治疗单个坏域；用熔断禁止新买治疗脏池。

## 3. 提交必须精确

子串匹配会点错按钮。「注册」会点到「使用邮箱注册」。

- 入口和提交用**整段文案相等**
- 提交后读页面再决定下一步，不要固定「等 N 秒没有下一框就再点一次」
- 同一资源在冷却期内禁止再次触发「发送」

## 4. 资源身份要归一

供应方卖的「变体」在目标站可能是同一身份。买到或列出后先算 `normalizeKey`。同一 key 已在用或已冷却 → 不提交。拉黑的是域 / 号段 / 归一 key，不是整类商品。

采购按**计数交错**，不要按金额补齐（金额补齐会在便宜类型失败后把预算砸到贵的一类）。类型可以软暂停，不要永久熔断。

## 5. 等待看对方做到哪一步

| 对方状态 | 等多久 | 要不要重提 |
|----------|--------|------------|
| 还没提交成功 | 短等 + 检查是否点错 | 最多精确再点一次 |
| 已寄出 | 加长窗口，轮询收件箱和列表 | 不重提 |
| 频控 N 分钟 | 冷却；同时捞旧信 | 不重提 |
| 收码接口抖动 | 单次超时重试，总窗口不变 | 不重提 |

## 6. 业务错误 vs 基础设施错误

两套分类器，不要混用。

- **业务层**（页面原文）：决定这条资源退、冷、等、换
- **基础设施层**（进程 / 主机 / HTTP）：超时、有限退避、降并发、延后副作用

单次业务尝试要有硬顶时间。超时只换通道，不把资源判死。

## 7. 任何一层都不能卡死整场

按空闲时间升级，而不是按失败次数关停：

1. 线程自己崩了：外层兜住，短等后继续
2. 数分钟无进展：刷新通道池
3. 更长无进展：降回最少并发，解开类型软暂停
4. 暂时买不到新资源：指数退避，不要退出进程
5. 池里全是冷却中的资源：仍允许新买
6. 看门狗与业务循环解耦（定时器 `unref`）

**停机只认明确的 STOP。不认「最近全失败」。**

## 8. 换到别的软件时的清单

1. 收集 ≥20 条真实失败原文，写成分类测试
2. 画出主路径四步，标出每一步禁止重放的动作
3. 供应方能力对上失败原因码
4. 写清归一规则
5. 采购按计数交错；失败拉黑到域 / 号段
6. 启动、HTTP、导入全部带超时；导入失败不回滚已成功的主产物
7. 主机负载进看门狗
8. 日志能区分：退役、冷却、类型暂停、启动失败、主机降载、看门狗、延后导入
