# 闭环：从能跑到能上线

开发完成 = 主路径在受控环境里绿了。  
真正上线 = 分类、证据、包装、灰度、观察、回滚、停机信号全部就位，并且连续跑过一个业务周期。

配套：[resilience.md](./resilience.md)

---

## 阶段 0 — 「做完」还不是「能上」

功能开发完成时通常只证明：作者知道怎么点；主路径在某一台机器走过；测试覆盖了作者想到的情况。

还没有证明：真实失败被分类；密钥不在安装包里；对方站点 / 供应方 / 主机负载会拖死整场时能换路；能停、能回滚、能看清现场。

## 阶段 1 — 合同

1. 用现在时写验收句，每句能写成测试
2. 画出主路径四步，标出禁止重放的动作
3. 列出外部依赖：超时、重试、失败后主产物是否保留
4. 列出密钥：哪些进环境 / 远程配置，哪些绝不能进安装包
5. 写下停机信号：只认 STOP

## 阶段 2 — 证据

先写红灯。至少 20 条真实失败现场。业务错误和基础设施错误两套分类器。每条分类只映射一种动作。

## 阶段 3 — 包装

1. 版本号能区分上一包
2. 安装包不含密钥、不含调试转储、不含上一轮脏库存
3. 配置可从 URL 加载，也可整段粘贴；机器访问不了域名时要有 IP 或离线粘贴
4. 第一次启动清单写进面板或一页纸：装内核 / 填配置 / 点启动 / 数据落在哪 / 怎么停
5. 未签名包写明系统会拦，以及如何放行
6. 下载目录关闭列表；带密钥的配置 URL 当密码保管

## 阶段 4 — 灰度

不要用「开发机跑通」代替灰度。

1. 最小火力：1–4 路，只跑一个完整业务周期
2. 日志能否分清：退役、冷却、类型暂停、启动失败、主机降载、看门狗、导入延后
3. 该交错的资源有没有变成只打最贵的一类
4. 有没有把「请 N 分钟后再试」当成「对方不认」然后连点提交
5. 内存掉到阈值时有没有降窗口

## 阶段 5 — 上线

旧进程先 STOP，再切新包，避免两套逻辑抢同一批资源。回滚条件预先写死。上线公告只发：安装地址、配置地址、怎么停。不发密钥明文到群。

## 阶段 6 — 上线后第一个小时 / 第一天

第一个小时：主路径至少成功一次；已知失败的动作与分类表一致；没有同一资源死循环；导入失败没有回滚主产物。

第一天：并发按设计上限跑过一个工作时段。任一小时级检查失败：降并发或回滚，不要「再观察一晚」。

## 阶段 7 — 日常

停机走 STOP 或面板停止，等在途尝试结束。密钥轮换：配置 URL 当密码。拉黑名单、跳过名单、延后导入队列要可持久化。每周把新的失败原文补进分类测试。

---

## 上线门禁（打印用）

- [ ] 验收句可测试，主路径四步标了禁止重放
- [ ] ≥20 条真实失败原文进了分类测试
- [ ] 业务分类与基础设施分类分开，每类一种动作
- [ ] 单测绿，主路径至少一条端到端绿
- [ ] 安装包无密钥；配置可 URL / 粘贴 / IP
- [ ] 开机说明、数据目录、STOP 路径写清
- [ ] 小并发灰度过了一个业务周期，无空转
- [ ] 旧进程已停，新旧不抢同一资源
- [ ] 看门狗、硬顶时间、降载、延后导入已打开
- [ ] 回滚条件写死，第一个小时的成功样本已看到

没勾完的那一项，就是还不能上线的原因。
