# 闭环：诊断 → 规格 → 红灯 → 实现 → 验证 → 反思

任何非琐碎改动走这 7 步。跳步的 PR 按流程拒，不按意图放行。

## 1. Diagnose

用三颗子弹写缺口，写在 PR / 任务描述里。每颗必须是**现在时、可观察**。

坏：「系统会更稳。」  
好：「域名被拒时仍会重提同一资源。」

没有失败原文，不准定性。先存：URL、可见正文、按钮文案、输入框 name、刚调用过的接口状态码（不含密钥）。

## 2. Spec

指出正在增加 / 修改 / 删除的不变量。没有 spec 的行为不准进主路径。

不变量写法：主语 + MUST / MUST NOT + 可测后果。

例：`一种分类 MUST 只映射一种动作。频控 MUST NOT 触发再次提交。`

## 3. Plan

拆 P0 / P1 / P2。每项有 Definition of Done。P0 必须能单独上线而不留下半套分类器。

## 4. Probe（红）

PR 的第一笔改动是**失败的测试或探针**。用对方页面 / 接口的**原文**，禁止只测自己编的枚举。

模板：[templates/CLASSIFIER.test.mjs](../templates/CLASSIFIER.test.mjs)

## 5. Implement（绿）

最小改动把红灯翻绿。禁止顺手清理隔壁文件。重构另开 PR。

## 6. Verify

证据来自测试 / CI / 分段日志，不来自「我这边可以」。把命令和关键输出贴进描述。

## 7. Reflect

同一份变更里追加新缺口到风险清单。分类器过期比代码过期更快：每周把新的失败原文补进测试。

---

## 反模式

| 说法 | 实际含义 |
|------|----------|
| 我顺手整理了附近代码 | 范围失控 |
| 本地能跑 | 没有证据 |
| 测试以后再补 | 没有以后 |
| 任务列表打了勾 | 构建说了算 |

---

## 和「创造力」的关系

这一环逼 AI 先结构化再动手。跳过 Diagnose 直接写代码，就是在用补全冒充创造。
